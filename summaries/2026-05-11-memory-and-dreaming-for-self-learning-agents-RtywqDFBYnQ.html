Memory & Dreaming pour agents auto-apprenants

Mahesh · PM Platform, Anthropic Durée : 24:28 Voir la vidéo ↗
Memory · Public Beta Dreaming · Research Preview Managed Agents API

TL;DR En 30 secondes

Anthropic présente Memory (en beta publique) et Dreaming (lancé en research preview ce jour-là) dans la Managed Agents API. L'idée : modéliser la mémoire d'un agent comme un système de fichiers que Claude gère lui-même avec bash/grep, le découper en memory stores avec des scopes de permissions (lecture seule pour la connaissance partagée, lecture/écriture pour la mémoire de travail), ajouter versioning + concurrence optimiste pour les essaims d'agents, puis lancer un processus asynchrone hors-bande (Dreaming) qui relit les transcripts de la veille, déduplique, consolide et enrichit la mémoire — pour que les agents du lendemain soient meilleurs sans coût de latence. Résultats annoncés : Harvey ×6 sur un benchmark juridique, Rakuten −90% d'erreurs au premier essai.

1 Actionables prioritaires

Ce que tu peux mettre en pratique dès maintenant si tu construis des agents.

[5:32]
A1

Modélise la mémoire comme un FS

Une hiérarchie de fichiers que l'agent gère via bash + grep. Évite les schémas rigides. Opus 4.7 est SOTA sur ce pattern.

[7:15]
A2

Découpe en plusieurs stores

Un store read-only pour la connaissance organisationnelle (runbooks, SLO) + un store read-write par équipe/tâche pour la mémoire de travail.

[7:59]
A3

Concurrence optimiste (hash)

Quand des dizaines d'agents écrivent en parallèle : précondition par content hash avant chaque update pour ne pas écraser le travail d'un autre.

[8:25]
A4

Audit log + attribution

Version history complet, qui a modifié quoi à quel timestamp depuis quelle session. À exposer aussi aux agents pour qu'ils raisonnent sur les changements.

[9:00]
A5

API portable, pas de lock-in

Branche un pipeline externe : PII scanning, nettoyage, clonage vers un système maison. Ne couple pas la mémoire au harness.

[14:11]
A6

Sépare deux objectifs

L'agent en session optimise la tâche. Le job Dreaming optimise la qualité de la mémoire. Ne mélange jamais ces deux objectifs.

[12:14]
A7

Trigger Dreaming intelligemment

Lance-le en cron (nuit) ou au spin-down d'un agent qui finit une tâche. Toujours hors du hot-path → zéro latence sur la session active.

[13:01]
A8

Diff + review humain avant apply

Dreaming produit un diff. Tu peux l'appliquer direct ou passer par une étape de revue via l'API. Penses-y pour les domaines sensibles.

[15:48]
A9

Compute upfront, amortis

Vois Dreaming comme un index de recherche : on dépense les tokens une fois en amont, des centaines d'agents lisent ensuite efficacement.

[21:41]
A10

Cherche les patterns cross-sessions

Un agent seul ne voit que sa session. Dreaming repère « 5 entrées identiques », « pic CPU + 60 s = retry », et les consolide en une note partagée.

2 L'architecture en un schéma

Agents en session (in-band, latence critique) Memory stores (file system, scopes) Dreaming (out-of-band, async)

3 Les 3 couches d'un système mémoire frontier

À [9:39] Mahesh formalise la conception en 3 couches indépendantes. Chacune se conçoit séparément.

① Storage

Où les données vivent.
  • Métadonnées d'attribution
  • Versioning / audit log
  • Concurrence (content hash)
  • Scopes de permissions

② Structure & content

Quoi et comment on encode.
  • Fichiers dans un FS (Memory)
  • Skills = mémoire procédurale
  • Hiérarchie gérée par Claude

③ Process

Quand et comment on met à jour.
  • In-band (l'agent lui-même)
  • Out-of-band (Dreaming)
  • Cron / post-task triggers
  • Diff + review humain

4 Memory vs Dreaming

In-band · temps réel

🧠 Memory

  • L'agent lit/écrit pendant qu'il travaille
  • Perspective locale (sa session, sa tâche)
  • Latence : sur le hot path
  • Outils : bash, grep
  • Beta publique dans Managed Agents API
Out-of-band · batch async

💭 Dreaming

  • Process indépendant, sur cron ou post-task
  • Perspective globale (n sessions, n agents)
  • Latence : zéro sur les agents en cours
  • Produit un diff à appliquer
  • Research preview (lancé le jour de la talk)

6 Démo SRE : ce qu'on voit en pratique

[17:49]Agent SRE écoute les alertes
Pour chaque alerte, il spawn un sub-agent de triage (ou un agent qui ouvre une PR).
[18:12]3 memory stores par agent
org-wide knowledge (RO, runbooks/SLO) · SRE memory (RW) · codebase memory (RW).
[18:49]P1 → investigation
L'agent vérifie CPU, traffic, PR récents, écrit ses findings dans le SRE store sous forme de diff.
[19:17]2e agent sur la même alerte
Lit la note du précédent → short-circuit immédiat de l'investigation. Gain tokens + intelligence.
[19:57]Audit log dans la console
Chaque écriture est horodatée, attribuée à un agent + une session, avec son precondition hash.
[20:47]Lancement d'un job Dreaming
Cible : le SRE store. Source : toutes les sessions des 7 derniers jours qui l'ont touché.
[21:41]Le diff produit par Dreaming
① ajoute une note « pattern : alertes 60 s après pic CPU = retry inefficace » que personne n'avait vu seul · ② consolide 5 entrées dupliquées · ③ supprime une entrée stale · ④ note de verification : la mémoire est à jour, fiable pour demain.

7 Insight conceptuel à retenir

« Dreaming suit les mêmes lois d'échelle que le test-time compute : tu dépenses plus de tokens en amont pour garder la mémoire organisée, et tu amortis ce coût sur tous les agents qui la lisent ensuite. C'est l'équivalent d'un index de recherche curaté pour des swarms d'agents. » — Mahesh, paraphrase de [15:48–16:51]

Autrement dit : Memory = la RAM tactique d'un agent ; Dreaming = la consolidation mnésique nocturne qui transforme la RAM d'un essaim en base de connaissance d'entreprise.
